# Scale test: one million customers

`scripts/scale_test.py` drives a throwaway copy of the application (own database, own workspace) through the whole path with a synthetic file and checks the result against
what was planted in it. The file (`gen_data2.py`, 1,001,460 rows, 141 MB) holds planted duplicates of nine kinds, look-alike companies, blank / over-long names, junk and
blank countries, test customers, deleted flags and spelled-out country names.

    python scripts/scale_test.py --base http://127.0.0.1:8768 --csv big1m.csv --truth big1m.truth.json --workspace <workspace> --pg <dsn> --skip-ai --lineage NONE --exclude-defects

## What it found, and what was changed

| Finding at 1,000,000 rows | Change |
|---|---|
| Duplicate matching peaked at 7.8 GB and took 560 s in the name comparison: ~100 million "similar name, different tax number" pairs were held as Python objects | The tax-number veto is decided for a whole chunk at once on numeric arrays and the vetoed pairs are only counted; blocks are streamed; comparison stops early below the review band |
| "Maria Garcia" in one city, with nothing else in common, was merged and labelled as address-backed | A name shared by 5 or more records (`common_name_count`), with no street / house number / postcode on both sides, is not merged: the pair goes to the review list and both records load |
| A shared phone number or e-mail linked two companies with different tax numbers | The "two tax numbers = two legal entities" rule now also holds for shared e-mail and phone; counted in `exact_links_vetoed` |
| Quality assessment 103 to 288 s | Not changed; 38 s on the quiet machine of the final run, so it was memory pressure from the dedup stage |

## Final run (fixed code, lineage NONE, rows with critical defects left out)

| Stage | Time |
|---|---|
| Land the file | 10 s |
| Profile | 5 s |
| Quality assessment (179 checks) | 38 s |
| Mapping, exclusions, approval | 7 s |
| Transform + deduplicate + validate | 100 s, server peak 1.84 GB (was about 28 min and 8.3 GB) |
| Sign-off, Cockpit workbook (999,031 partners, 5,994,026 rows), sandbox SAP load | 190 s + 232 s, 999,031 loaded, 0 failed |
| Reconciliation certificate | 4 s |

Checks, all passed: the counters add up (850 excluded + 1,160 duplicate children + 419 rejected + 999,031 valid = 1,001,460); every planted duplicate kind was caught (one
"The ..." copy was left out of the run by a rule before matching); no look-alike was merged; no merged group holds two different tax numbers; none of the must-not-load
sets (blank name, over-long name, test customer, deleted flag, junk or blank country) reached the loadable file; all 160 "Maria Garcia" records stayed separate.

## Limits of this evidence

* The data is synthetic and was generated by the same person who wrote the matcher; a real legacy file will be messier.
* One machine, 3 to 5 GB of free memory, a local PostgreSQL. The SAP side is a stand-in gateway.
* Lineage `ALL` (a lineage row per transformed cell) costs about 9 extra minutes and 16 million rows (2.4 GB) per run at this size. The default for large tables should stay
  EXCEPTIONS or NONE.
* The assistant answers at this size were not timed with Gemini. With the local 7B model on CPU each question took about 280 s (two model calls); without a model the data
  tools answer in 4 to 8 s. In that fallback mode a question like "find customers named X" returns the run summary instead of searching: the model is needed for routing.
* Database delivery (as opposed to the workbook and the sandbox load) was not exercised at this size.

# Second dataset: a German-style ERP export

A differently shaped file, because the matcher had been tuned against the first one: `scripts/gen_scale_dataset_de.py` (1,000,000 rows, `;` delimited, German column names,
accents, ISO-2 / ISO-3 / German / English country spellings, 40% people and 60% companies, Zipf-distributed surnames so a few names fill huge blocks). Its duplicates carry **no
contact data** (only the name and address can find them): umlaut transliteration, "Müller, Hans" against "Hans Müller", legal-form variants, "Str." abbreviations, typos,
case and spacing. Its traps: same name with a different tax number, branches sharing a phone number, homonym people in one city, "Werk 1" / "Werk 2", different firms at one address.
The mapping, exclusions and what must never load travel inside the truth file (`profile`), so `scale_test.py` runs any dataset.

| What it found | Change |
|---|---|
| The tax column is called `UST_IDNR` (the German VAT-ID name) and was not recognised: no tax key, no tax veto. 2,994 of 3,000 look-alikes with different tax numbers and every shared-phone pair were merged | Tax column detection knows the national spellings (UST, USTID, STEUERNR, SIRET, PIVA, NIP, ...); a table with no tax column now says so in the dedup warnings |
| `Großbritannien` never matched its lookup entry: DuckDB upper-cases ß to ẞ, Python to SS | One SQL fold shared with the Python key (`_duckdb_util.fold`), used in the lookup join and the country quality rules |
| `token_sort_ratio("EVA ÇELIK", "EVA CELIK")` is 44: an accent changes which word sorts first | Names and addresses are folded before comparing (ä = ae, ß = ss, every other accent dropped) |
| "Müller, Hans" and "Hans Müller" never met: the first blocking key was the start of the name, not of the sorted words; address blocks of "Hauptstraße" are huge and are only compared window-wise | Blocking on the sorted words; a third pass on house number + postal code (very selective); that pass also compares the names without spaces ("Claudi aHuber") |
| A record without a tax number could join two companies with different ones (56 groups) | Clustering refuses the link that would put two tax numbers in one group, strongest evidence first; a person's decision is never refused. Reported as `chain_links_refused` |
| 654 s in the name comparison: with no tax veto, every similar-name pair of 400,000 people went through a Python loop | The "different digits in the name" and "different house number / postal code" decisions are made on numpy arrays; 222 s, identical result |
| The pre-submission check blocked the mapping (100% of rows failing on the language field) | Not an application fault: SAP's language key is one character and my mapping sent "DE". The check was right and said what to do |

## Final run

| Stage | Time |
|---|---|
| Land, profile, quality assessment | 10 s, 5 s, 11 s |
| Transform + deduplicate + validate | 271 s, server peak 2.21 GB |
| Cockpit workbook (5,370,837 rows) + sandbox SAP load (968,704 partners, 0 failed) | 180 s + 222 s |

Counters add up; no merged group holds two different tax numbers; none of the must-not-load rows (blank / over-long name, TEST, ZZ_, deleted, junk or blank country, e-mail without
@) reached the loadable file. 27,968 duplicate children. Of the 28,000 planted duplicates, 81 are not merged, and of the 13,500 traps 19 were merged. The remaining ones are
mostly the generator's own doing: the "Werk 1" trap renames an original after its copies were made (the pair then differs in a number, on purpose), and a tax-less copy of
a record that has a look-alike twin at the same address is attached to one of the two, which is right but not the one the truth file expects (28 of 37 such pairs merge when run
alone). What was the application's: 13 homonym people who share city, postal code AND house number but not the street name were merged (the name carries 65% of the
score). The street is now checked on its own: a pair whose streets are plainly different (similarity under 60, where "Hauptstr." / "Hauptstraße" and a typo stay far above) goes
to the review list instead (`street_conflict_pairs_held_back`). Rerun: 0 homonym merges, 85 of 28,000 planted duplicates not merged (the same generator artifacts), counters add up,
no group with two tax numbers. A space typo ("Claudi aHuber") is only found when the address matches, deliberately: without an address the spaceless comparison would be weak
evidence, and a record with an e-mail, phone or tax number is linked by those anyway.

## Limits of the second run

* The first dataset's file and generator were deleted from the scratch folder before the changed matching could be rerun on it, so its numbers above are from before the
  second round of matching changes. The unit tests (724 passed, 72 skipped for want of the real-server containers) pin what the first dataset found.
* Same synthetic-data, one-machine, stand-in-SAP caveats as above. The assistant was run without a model.
