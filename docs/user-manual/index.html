1Introduction

What this manual is, who it is for, and how to read it.

1.1Purpose of this manual

This manual describes how to use the ERP Migration Accelerator, a web application that moves master data (here: customers) from a legacy source into SAP S/4HANA (Business Partner), or into a database or Google Firestore, under controls that make the result provable. It explains the process end to end, the role of each person involved, every screen and button used, and the evidence the application produces.

1.2Who should read it

ReaderRead chaptersWhy
Migration author (builds the mapping)2, 3, 4, 5, 6The whole procedure, from registering a source to a delivered run.
Approver / steward (reviews, approves, signs off, loads)3, 6.7 to 6.14, 7Your decisions and the evidence you rely on.
Auditor or project owner2, 3, 7, 8How the controls work and where the proof is.
Administrator4, 9, appendices C and DInstallation, settings and what was and was not tested.

1.3Scope and what was verified

The manual covers every function of the application as of the build named on the cover. All screenshots are real: they were taken by a script that operated the application exactly as a person would, on a practice file of 1,980 invented customers (mock_data/legacy_ar_customers.csv). Only the red numbered rings were added, to point at parts of a screen.

Caution

SAP itself was not used. Every SAP delivery in this manual went to a stand-in gateway that follows SAP's published interface. It proves that the application builds correct messages and handles success and failure; it does not prove that a particular company's SAP system will accept them. Appendix D lists what was tested against what.

2Concepts and architecture

The ideas the rest of the manual relies on.

2.1The migration in one paragraph

Data is read from a legacy source and frozen into a locked snapshot. It is profiled and quality-checked. A mapping set (a list of rules) says which legacy column fills which SAP field and how. A second person approves the rules, after which they are locked. A run applies them to every row, finds duplicates and validates against SAP's constraints. The gate blocks while critical defects remain. A named steward signs off, the data is delivered and read back, and a reconciliation certificate proves that every source row is accounted for.

Figure 1. Architecture: sources are only read; the application keeps the snapshot and the catalogue; results go to a target, with evidence.

2.3Glossary

Source / legacy
The old system or file data is read from. Never modified.
Snapshot
A locked copy of the source taken at registration; all later work uses it. It has a row count and a fingerprint.
Fingerprint (hash)
A short code computed from the data; it changes if any value changes. Used to prove two data sets are identical.
Control total
The row count you expect, entered at registration. A different count stops the registration.
Key
The column (or columns) whose value is unique per row, such as CUST_ID. It lets every finding name the exact record.
Profile
Statistics per column: type, blank ratio, distinct values, lengths, most frequent values, a masked sample, a health score.
Mapping set / rule
A set is the complete list; a rule fills one SAP field from legacy data. Kinds: DIRECT_COPY, STATIC_VALUE, VALUE_MAPPING, SQL_EXPRESSION.
Lookup
A dictionary inside a VALUE_MAPPING rule, for example Deutschland → DE. Matching ignores letter case.
Status
DRAFT (editable), SUBMITTED (awaiting a second person), APPROVED (locked).
Run
One complete pass of all rows through an approved mapping set, with validation and de-duplication.
Defect
A group of rows that broke one rule, with examples and a root cause. Severities: CRITICAL, HIGH, MEDIUM, LOW. Only CRITICAL blocks the gate.
Gate
The release check of a run: BLOCKED while a critical defect is open, READY FOR LOAD when none is.
Exclusion
A rule that leaves rows out on purpose, with a recorded reason. Excluded rows are kept, not deleted.
Sign-off
A steward's recorded acceptance of a run that passed the gate. Required before load.
Target
Where data is delivered: SAP (workbook, sandbox, live OData), a database, or Firestore.
Certificate
The reconciliation report: every source row accounted for, every control listed, who approved and signed off.
Rollback
Removal of exactly the rows one delivery wrote (each row carries its run number).
Content pack
An exported approved mapping (rules, lookups, exclusions; no customer values) reusable in another migration.

3Roles and responsibilities

Who does what, and what the application prevents.

3.1Roles

The application records the name in the Acting as box (top right of the window) against every action. In an installation with API keys configured, the name comes from the person's key; without keys, anyone may type any name, which is acceptable for practice and not for real data (see 4.4).

RoleMayMay not
AuthorRegister sources, profile, write or generate rules, test them on a sample, exclude rows, submit a mapping set, run an approved set.Approve a set they submitted.
ApproverRead a submitted set and approve it (rules are then locked).Approve their own submission.
StewardSign off a run that passed the gate; execute the load; verify; roll back.Sign off a run whose mapping they authored (default policy).
AdministratorInstall, configure, manage keys, allowed servers, who may approve (MIGRATION_APPROVERS).Bypass the gate.
AuditorRead the certificate, audit log, compliance page, dashboard.(read only)
Figure 3. Who may do what. The author prepares and submits; a different person approves; the gate and the sign-off protect the target.
Control

Segregation of duties. The application refuses an approval by the author of the set. The certificate lists the author and the approver and fails its control check if they are the same person.

4Getting started

Requirements, installation, the main window and the settings that matter.

4.1Requirements

ItemRequirement
ServerA computer that runs Python 3 (the practice runs used Python 3.13 on Windows 11); the catalogue needs PostgreSQL (Docker is the quickest way)..
BrowserA current Microsoft Edge or Google Chrome. The user interface is a single web page; nothing is installed on user computers.
DiskA workspace folder for snapshots and run results. It holds copies of customer data: back it up and treat it as confidential.
AI (optional)Either Ollama with a local model (default qwen2.5-coder:7b; needs about 6 GB of memory and runs on a CPU, slowly) or an online Gemini key. Everything except AI mapping works without either.
SAP (optional)For live delivery: the address of the SAP OData service and a technical user. Without them the sandbox stand-in and the Migration Cockpit workbook are available.

4.2Installation

# 1. a PostgreSQL database for the catalogue
docker compose up -d postgres

# 2. Python packages
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt

# 3. settings: a file called .env in the project folder
DATABASE_URL=postgresql+psycopg2://migration:<password>@localhost:5432/migration_catalog
MIGRATION_WORKSPACE=workspace

# 4. create the tables and load the SAP field catalogue
.venv\Scripts\python -m alembic upgrade head
.venv\Scripts\python -m src.seeds.seed_sap_catalog

# 5. start the application, then open http://127.0.0.1:8000
.venv\Scripts\python -m uvicorn --factory src.api.main:create_app --host 127.0.0.1 --port 8000
Note

After upgrading to a build that changes the SAP catalogue (for example the German column-name aliases), run step 4 again so the new descriptions are loaded.

6Procedures

One procedure per task, in the order of a migration.

6.1Register a file source

Figure 7. Registration: read every row as written, keep all values as text, count, and fingerprint.
PR-1 Register a source from a file
Purpose
Freeze an extract file into a locked snapshot with a verified row count.
Performed by
Author
Before you start
The extract file, the expected number of rows (control total), the name of the column(s) that identify a row.
Procedure
  1. In the toolbar press New Source. A five-page wizard opens.
  2. Page 1. Give the source a name, for example LEGACY_ERP (the name of the legacy system; one system can hold many tables). Leave Database on Extract file and Provider on Auto-detect.
  3. Page 2. Choose the file and press Test. The wizard reports the detected format, encoding, delimiter and column count.
  4. Page 3. Enter the table name (AR_CUSTOMERS), tick the key column (CUST_ID) and enter the control total (1980).
  5. Page 4. Tick Profile the table now. Page 5 shows a summary; press Finish.
Expected result

The wizard closes, a Profiler tab opens and a message reads Source LEGACY_ERP / AR_CUSTOMERS registered: 1,980 rows, 10 columns.

Note

A shorter route exists for a plain file: the Sources page (shown in 6.2) has a Register a legacy source form with the same fields and a Register & upload button.

Caution

If Test shows everything in one column or damaged accents, change Delimiter or Encoding and test again. If the row count differs from the control total, registration stops: obtain a complete extract or correct the number.

Control

The source is only read. All values are stored as text so nothing is rounded or re-typed. The row count and fingerprint of the snapshot are recorded and appear on the certificate.

6.2Register a database, document store or cloud source

PR-2 Register a database, Firestore, MongoDB or cloud-storage source
Purpose
Read a table or collection from a live system into a snapshot, without installing anything on it.
Performed by
Author
Before you start
The server address (or project), a read-only account, and permission to connect. In production, list the permitted servers in MIGRATION_DB_ALLOWED_HOSTS.
Procedure
  1. Press New Source and enter a name (letters, digits, . _ -, up to 64).
  2. In Database choose the kind: PostgreSQL, SQL Server, Oracle, MySQL, MongoDB, Google Firestore, or cloud file storage (Azure Blob, S3, SFTP). The Provider line shows the driver used.
  3. Connection. Enter server, port, database, user and password (or, for Firestore, the project and service-account file) and press Test. The wizard really connects.
  4. Tables. Browse the schemas and tables (or collections), choose one, set the key and the control total, and finish as in PR-1.
Expected result

The chosen table or collection is read, counted against the control total and frozen. For MongoDB and Firestore each document becomes one row and nested fields become dotted column names (for example address.geo.lat).

Control

A password is never written to disk and never echoed back after a failed attempt. MongoDB is read-only by design. Firestore bills one read per document; the wizard says so next to the driver.

6.4Assess data quality

PR-4 Assess data quality
Purpose
Run a library of tests and receive ranked findings with a recommended action each.
Performed by
Author
Before you start
A profiled table.
Procedure
  1. Select the table and press Quality.
  2. Press Assess data quality now.
  3. Sort the findings by severity and read the what to do column.
Expected result

A score, the number of tests run and a findings table ranked worst first.

FindingMeaning
HIGH T03 Tax number used by several partners120 customers share a tax number: duplicates, branches or a typing error. A person decides.
HIGH C01 Not a country44 rows name Wakanda, Narnia or Atlantis.
MEDIUM E03 E-mail sharedA shared mailbox is fine; one person's address on several customers usually is not.

A score of 99.4 is an average over many tests; a few rows with a grave problem hardly move it. Read the findings, not only the score.

6.5Combine tables

Figure 22. Combining tables. The preview refuses a join that would silently repeat records.
PR-5 Combine registered tables into one source table
Purpose
Join and filter tables you already registered (for example customers and payment terms) into one new source table, before mapping.
Performed by
Author
Before you start
Two or more registered tables with a column that matches.
Procedure
  1. Press Combine in the toolbar.
  2. In Start from choose the first table; every record of it is kept unless a filter or an inner join removes it.
  3. Press + Add a table to join. Choose the table, the column on each side and how to compare (ignoring blanks and letter case, or exact).
  4. Optionally press + Add a filter (keep records where …).
  5. Press Preview on my data. Read the counts: records in the first table, rows after joining, and for each join how many records find no partner.
  6. If the preview is accepted, enter the System name, the Table name and the Primary key column(s) and press Create table.
Expected result

A banner reads Created table #N with R rows and links to the Profiler. The new table appears under Sources and is used like any other source; the snapshot records which tables it was built from, so it can be rebuilt.

Control

A join that would repeat records is refused unless you tick Allow a join that repeats records, in which case the preview says so in plain words. Nothing is written until you press Create table.

6.6Write the mapping

PR-6 Create a mapping set
Purpose
State, per SAP field, which legacy column fills it and how.
Performed by
Author
Before you start
A registered, profiled table.
Procedure
  1. Select the table and press Mapping (or double-click Mapping Studio under the table).
  2. Create rules in one of two ways, or both: Generate AI mapping (6.6.1) or New empty mapping set followed by Add manual rule (6.6.2).
  3. Complete lookup dictionaries (6.6.3).
  4. Press Check rules on sample (6.6.4) until it reports that the set can be submitted.
Expected result

A DRAFT mapping set with a card per rule, each showing the legacy column, the SAP field and its length, the kind of rule and a sample pass rate.

6.6.1 Let the AI propose

Figure 28. AI mapping: the model chooses only among SAP fields found by a semantic search, and every proposal is checked by rules and by people.
  1. Press Generate AI mapping. Choose a consistency level if offered.
  2. The job runs on the server; a progress bar shows the column being examined. You may leave the page.
  3. Review every proposal: confidence, reason and the tag AI-suggested.
SafeguardWhat it does
Candidate retrievalThe model may choose only among the closest SAP fields found by meaning (including German names such as Firmenname).
Rule validatorParses SQL, allows only listed functions, rejects absurd lengths, and marks rules that rewrite values (padding, replacing, translating) NEEDS_REVIEW.
Value checkSamples real values: if most are not valid country codes, a country rule is marked for review.
ColoursGreen: confident (over 85%). Amber: review (60 to 85%). Red: blocked (under 60%). Never auto-approved.
Human approvalNothing takes effect until a second person approves the set.
Caution

What the AI does not do. In the evaluation recorded in docs/ai-evaluation.md it proposed plain copies and chose the right SAP field for 34 of 34 test columns after the German-alias fix. It did not invent the country dictionary, the payment-term codes or the fixed values your business must supply. Confidence percentages did not by themselves separate right from wrong answers; the value check did. On a CPU-only laptop a local 7B model needs minutes per column; an online model is faster if policy allows it.

6.6.3 Complete the lookup dictionaries

  1. On a VALUE_MAPPING rule press Edit.
  2. In Lookups enter pairs as {"old value": "new value"}.
  3. Tick Confirm as reviewed (you state that you read them) and press Save rule.
Note

Matching ignores letter case: USA → US also finds usa and Usa.

6.6.4 Check the rules on a sample

  1. Press Check rules on sample. The rules are applied to the real rows as a dry run; nothing is saved.
  2. Read the result: whether the set can be submitted, warnings, the pass rate and What to do next.
Note

A warning does not prevent submission. The 10% that fail are exactly what the gate will list after the first run (6.9).

6.7Submit and approve

PR-7 Submit a mapping set and approve it
Purpose
Obtain an independent review; lock the rules.
Performed by
Author submits; a different person approves
Before you start
A DRAFT set whose check passed.
Procedure
  1. As the author press Submit for approval. The status becomes SUBMITTED.
  2. Change Acting as to the approver's name (in a keyed installation the approver signs in with their own key).
  3. Read the rules and press Approve.
Expected result

Status APPROVED, with the approver's name and time. The rules can no longer be edited.

Control

An approval by the author is refused (segregation of duties). The approval is part of the audit trail and the certificate.

6.8Run the pipeline

Figure 40. The run. Every row ends in exactly one place.
PR-8 Run an approved mapping set
Purpose
Convert, de-duplicate and validate every row.
Performed by
Author or steward
Before you start
An APPROVED mapping set.
Procedure
  1. In the Mapping Studio press Run pipeline.
  2. Wait; a Governance tab opens when the run ends (seconds for thousands of rows; the scale test processed 1,000,000 rows, see docs/scale-test.md).
Expected result

The Governance page of the new run.

Control

The accounting identity always holds: left out + merged + rejected + valid = rows extracted. A row cannot disappear without a reason.

6.10Correct the rules and exclude rows

PR-10 Create version 2 and run again
Purpose
Resolve the defects in a new, editable copy; the approved set stays as evidence of run 1.
Performed by
Author, then approver
Before you start
A run whose gate is BLOCKED.
Procedure
  1. In the Mapping Studio press Check rules on sample again. Under Needs your approval read each Fix-it card: the situation, the proposed change and how to undo it. Enter any value the card asks for and press Yes, go ahead. A new draft (a copy) is created.
  2. Open Rows to leave out. Choose a column, a condition and a reason, press Check how many rows, then Leave these rows out.
  3. Edit rules as needed: add WHEN-RECEIVED → CASH to the payment-term lookup; change the name rule to left(trim(CUST_NAME), 40).
  4. Press Check rules on sample until 100% pass; then submit, approve (a different person) and run (PR-7, PR-8).
Expected result

The new run's gate reads READY FOR LOAD with no open critical defects.

Caution

Leaving out 147 customers (7%) is a business decision. The application makes it visible, recorded and reversible; it does not take it for you. Cutting a name at 40 characters can cut a word in half: it is the quickest fix, not the neatest.

Control

Excluded rows are not deleted. They are kept with the reason and listed on the certificate under EXCLUDED_BY_RULE.

7.2What the controls do not cover

  • Who the user is. Without MIGRATION_API_KEYS a typed name is trusted. There is no company single sign-on.
  • Whether a business decision is right. The application records excluding 147 customers; it does not judge whether that is acceptable.

8.2Frequently asked questions

Can the original data be damaged?
No. It is only read; all work is on a snapshot.
Can I use my own file?
Yes. CSV, Excel, JSON, fixed-width and Parquet files, databases (PostgreSQL, SQL Server, Oracle, MySQL), MongoDB, Firestore and cloud storage are supported.
Is the AI required?
No. Everything can be done by hand; the AI proposes and a person decides.
Is customer data sent to the internet?
Not with the local model. With Gemini, column names and a few sample values are sent for mapping; ask the administrator what policy applies. The assistant never sends customer records.
What if I change my mind after delivery?
Roll back (PR-17), correct, and deliver again.
What does “sandbox, simulated” in the status bar mean?
The application is connected to the SAP stand-in, not to a real SAP.
